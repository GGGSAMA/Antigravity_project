# 修仙实体组件架构设计书 (Domain-Driven ECS Architecture)

*本文档为纯理论架构设计，用于探讨和界定游戏中所有角色实体（玩家、NPC、妖兽）的数据组织与性能优化规范，不涉及底层代码的直接修改。*

## 核心设计理念

为了彻底解决“全场景任意组件高频读取同一节点造成的帧耗时上涨”以及“属性节点无限膨胀难以维护”的核心痛点，我们将废弃单一大锅炖式的 `CharacterData` 或 `Stats` 节点，采用**四层子节点解耦方案**。

这套设计严格遵循**高内聚、低耦合、单一职责**原则，完美贴合 Godot 引擎的节点特性。

---

## 一、 四大独立属性层定义

所有角色实体在 3D 场景中实例化时，其根节点下必定挂载这四个互不侵入数据的专属子节点：

### 1. `RootGenAttr` (本源根骨层)
* **职责**：存储先天静态基底数据（五行灵根权重、灵根品级、先天天资、修为大境界）。
* **特征**：**极低频变更**。不参与战斗实时运算，不存储临时战斗数值。只在角色创建、吃下逆天改命丹药、或突破境界时，才会发射变动信号。
* **数据流向**：向下只读，产出“本源修正倍率缓存”（伤害系数、修炼效率系数）。

### 2. `SpiritMindAttr` (神识神魂层)
* **职责**：专属中后期的精神域体系（神识强度、神识探测范围、神念消耗、心魔阈值）。
* **特征**：完全独立于五行灵根体系。未来开发“神识威压”、“夺舍”、“搜魂”机制时，只在这一层做加法，绝不污染物理战斗层。

### 3. `CombatRuntimeAttr` (战斗动态层)
* **职责**：高频波动的临时数据容器（当前气血 HP、当前灵力 Mana、临时攻防抗性 Buff、技能冷却修正、临时遁速倍率）。
* **特征**：**极高频运算**。施法、移动、受伤时，只会访问此节点。它会在内部自动拿取 `RootGenAttr` 的缓存倍率做预计算，绝不去遍历灵根属性做重复乘法。

### 4. `SocialFactionAttr` (社交阵营层)
* **职责**：处理角色在社会关系中的属性（宗门声望、善恶业力、好感度、NPC 派系标记）。
* **特征**：只在非战斗的 UI 交互（对话、交易、情报打听）时被唤醒和读取。战斗中全程静默。

## 二、 架构优势推演

### 1. 彻底解决大地图性能痛点 (LOD 深度休眠)
当数千名 NPC 在同屏外运作时：
* 我们可以**彻底停用 (Disable Processing)** `CombatRuntimeAttr` 节点，省去所有 HP/Mana 的帧计算。
* 但依然保留 `RootGenAttr` 和 `SocialFactionAttr`，供后台推演系统（如岁月流逝、境界自动挂机突破、阵营恩怨计算）使用。
* 实现了完美的**动静分离**。

### 2. 杜绝信号风暴与耦合乱麻
* 如果采用旧方案，一次普通的回血，都会导致监听整个大节点的无关组件被唤醒。
* 新方案下，**信号粒度极度精准**：灵根变动只广播给养成模块，移动遁术模块只会收到 `CombatRuntimeAttr` 发出的移速改变信号。互不干扰。

### 3. Godot 实例化复用与存档结合
在 Godot 的落地实践中：
* **数据源**：后台依然可以保留极其轻量的 `CharacterData` Resource 作为“魂”（方便纯数据流存盘）。
* **场景实例化**：当角色进入玩家视野，实例化 3D 预制体（包含四大层节点）作为“肉身”。并将 Resource 里的数据**单向注入**给 `RootGenAttr` 和 `SocialFactionAttr`。角色离去时，仅将关键数据回写入 Resource。

---

## 三、 遗留技术债的割肉手术评估

要完成向本架构的迁移，面临最大的挑战是处理现有的 `components/stats.gd`（一个包含了血量、法力、寿命、悟性等所有属性的庞然大物）。
**建议的处置方案：**
1. 将 `stats.gd` 中的 `current_health`, `current_mana` 抽离，并入新设计的 `CombatRuntimeAttr`。
2. 将 `age_days`, `aptitude`, `cultivation_level` 抽离，并入新设计的 `RootGenAttr`。
3. 重写 Player UI（如血条蓝条面板），使其信号监听目标从旧 Stats 节点转移至 `CombatRuntimeAttr`。
