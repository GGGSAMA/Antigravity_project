## Game Design & Code Standards
1. **Data-Driven Architecture (No Magic Numbers)**: DO NOT hardcode configuration values, parameters, or random magic numbers in code. Whenever defining weights, probabilities, or logic parameters, expose them to the Godot Inspector using @export variables on components or scripts. Ensure designers can easily adjust parameters from the UI.
2. **GDScript Header Documentation**: EVERY GDScript file must have a detailed comment header at the top. This header must explain the script's overall function, structural logic, and specific settings/descriptions of its responsibilities.
3. **Character-Driven Empathy (角色演绎代入法)**: When designing narrative or combat outcomes, do NOT rely on the real-world player's reaction. The in-game Player Character (and NPCs) MUST act out the tragedy/joy autonomously through text bubbles, inner monologues, or log entries. If the PC's items are stolen, the PC must express anger/grief in-game, creating a theatrical performance that draws the player into empathizing with them (like in Tale of Immortal / 鬼谷八荒).

## Godot Engine Architecture Red Lines (防呆护城河)
1. **Node Path Fragility (禁止跨界爬树)**: Any encapsulated Scene MUST be a black box. NEVER use `get_parent()` or `get_node("../../")` to reach outside the current scene. Cross-module communication MUST use a segmented EventBus. Internal node communication must use root node delegation to sub-components or exported variables.
2. **No Polling in _process (禁止脏轮询)**: NEVER write business logic state checks (e.g. `if health <= 0`, `if inventory_full`) inside `_process()` or `_physics_process()`. The process loop is strictly for physics movement, animation interpolation, and timers. ALL state changes MUST be Event-Driven via Signals emitted at the exact moment data changes.
3. **Data vs. Logic Component Separation (数据与行为隔离)**: Adhere strictly to the Entity-Component architecture, but explicitly separate Data Components (holding pure numerical state, dicts, for saving/loading) from Behavior Components (handling inputs, physics, routing). Do not mix persistent sandbox state with frame-by-frame execution logic.
4. **Autoload Strict Governance (严格控制单例)**: NEVER use Autoloads for business logic or runtime state (e.g. Input Managers, Inventory). Autoloads are STRICTLY reserved for: ① Stateless EventBus ② Read-Only Static Config Managers ③ Core Systemic Drivers (e.g., TimeManager). All other managers must be attached to the SceneTree and destroyed on scene change to prevent memory leaks.
5. **Global Signal Lifecycle (防信号幽灵)**: When subscribing to global EventBus signals, you MUST manage the lifecycle. Unmanaged global signal subscriptions will cause fatal memory leaks and crash the sandbox. Disconnect in `_exit_tree()` or use Godot 4's strict Callable bindings.

## Software Engineering Workflow (Anti-Amnesia & Anti-Deadlock)
1. **Interface-First (空壳存根先行)**: Before writing the internal logic of any new system, generate Stub scripts. Use duck-typing (`has_method`) for interface contracts, but ALWAYS use Constant Strings (e.g., `const METHOD_TRY_INTERACT = "try_interact"`) for the method names to prevent silent typo failures. The engine MUST run without errors before internal logic is written.
2. **Bottom-Up TDD Execution**: You MUST utilize your TDD skills to test discrete components in isolation. Do not attempt to write a top-down manager and all its sub-components in a single turn. Write the smallest leaf component, test it, and then move up.
3. **Artifact Reading (架构缓存唤醒)**: At the start of any complex development turn, proactively use the view_file tool to read `docs/project_api_registry.md` AND `implementation_plan.md` or `master_design_document.md` to restore architectural context. This consumes minimal tokens while preventing Amnesia and spaghetti code.
4. **Global API Registry Maintenance (全局接口注册表)**: The project maintains a central Markdown file named `docs/project_api_registry.md`. WHENEVER you create a new class, node, or define a new dictionary/parameter structure, you MUST proactively append its interface (module -> class -> node -> interface/params) to this registry file BEFORE or IMMEDIATELY AFTER writing the code. Do not skip this step.
5. **Detailed Class/Function Documentation**: Every class and function you write MUST be fully documented at the top of the file/function. Never skip documenting the design intent of the class and the inputs/outputs of its functions.
6. **Anti-Spaghetti & Lazy Hotfix Prohibition (严禁随地拉屎)**: When asked to fix a bug or add a feature, DO NOT default to the easiest/laziest implementation (e.g., hardcoding `Input.is_action_pressed` in UI scripts, or using `get_node()` to violently cross module boundaries). You MUST evaluate if the fix violates architectural decoupling. If a quick fix creates tight coupling, you MUST reject the quick fix, propose a clean decoupled architecture (like EventBus or State Routing), and write it properly. Do not write crappy code just to satisfy the immediate surface-level requirement.
7. **AGENTS.md Backup Routine**: WHENEVER you refresh or update this `.agents/AGENTS.md` file, you MUST immediately create/update a backup copy of it in the `docs` folder (e.g., `docs/AGENTS_backup.md`).
